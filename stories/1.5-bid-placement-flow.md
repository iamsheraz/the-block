# Story 1.5 — Bid placement flow

**Status:** Ready
**Estimate:** 105 min
**Depends on:** Story 1.4

## Story

Make the bid panel from Story 1.4 actually place bids. Wire `useBids().submitBid` through to `dataStore.submitBid`. Add the confirmation modal that surfaces decision context — bid delta, reserve status, time remaining, worst damage note, commitment line. Handle success and error states. Persist bids in localStorage so they survive reloads.

## Acceptance criteria

- **AC1** Place Bid opens `BidConfirmationModal` showing: bid amount, delta vs starts-at (or vs current-bid), reserve status in plain English ("Below reserve by $800" / "Above reserve" / "No reserve"), time remaining, worst damage note (if `damage_notes` is non-empty), commitment line ("By placing this bid you commit to purchase if you win"), Cancel and Confirm Bid buttons.
- **AC2** Confirm Bid runs `validateBid` via the dataStore. On success: modal closes, success toast or inline confirmation renders showing the new high bid and the position relative to reserve. On failure: error state renders inline within the modal — most common case is "Someone bid $X first. Try $Y or higher." with an Adjust Bid button that pre-fills the new minimum.
- **AC3** Confirm Bid button shows loading state during submission (disabled, spinner). Cannot be double-clicked.
- **AC4** Modal traps focus on open. ESC and clicking the backdrop both close. Focus returns to the Place Bid button on close.
- **AC5** After a successful bid: the vehicle card on the inventory grid reflects the new `current_bid`, the detail page bid panel updates, and `BidHistory` on the detail page lists the bid with timestamp.
- **AC6** Bids persist across reload via localStorage. Reopening the detail page shows the bid history intact. Bidder identity (`localStorage` UUID) is stable across the session.
- **AC7** A bid that fails client-side validation (`validateBid` rejection) never reaches the modal — the bid input on the panel shows inline validation copy and the Place Bid button stays disabled.

## How to verify (UI)

1. `npm run dev` — visit a vehicle detail page.
2. Enter an amount below the minimum (or 0) in the bid input — inline error appears, Place Bid stays disabled.
3. Enter a valid amount, click Place Bid — modal opens with: bid amount, delta vs starts-at, reserve status, time remaining, worst damage note (if applicable), commitment line.
4. Tab through the modal — focus stays inside it.
5. Press ESC — modal closes.
6. Reopen, click Cancel — modal closes.
7. Reopen, click Confirm Bid — loading spinner briefly, modal closes, success state renders showing the new high bid.
8. Scroll to "Your bid history" below the fold — your bid is listed with timestamp.
9. Refresh the page (`Cmd+R`) — bid history is still there.
10. Navigate back to inventory — the card for this vehicle shows the new `current_bid`.
11. Try to bid on an ended auction (find one whose status flipped) — error state surfaces with "Auction has ended".
12. Place a bid, open the modal in a second tab, place a different bid, return to first tab and confirm — error state shows "Someone bid $X first. Try $Y or higher." with an Adjust Bid button that pre-fills the minimum.

## Watch for / Notes

- The "worst" damage note for the modal heuristic: first mechanical-classified note if any exist (mechanical issues outrank cosmetic for buyer concern), else the first damage note. If `damage_notes` is empty, the row hides entirely.
- The Adjust Bid button on the error state pre-fills the bid input with `new_current_bid + MIN_BID_INCREMENT` and keeps the modal open in form mode.
- Bidder identity is a stable UUID stored in localStorage under a separate key from bids. Clear localStorage = new bidder.
- The optimistic update pattern: `dataStore.submitBid` writes to localStorage immediately, fires subscribers, the UI re-renders. Because there's no remote server, there's no rollback path — the architecture is shaped for a future backend to add one inside `dataStore` without touching consumers.
